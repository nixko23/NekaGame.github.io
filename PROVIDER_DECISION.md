# Playback provider decision

**Verified:** October 25, 2026 against the linked official provider documentation and terms.
**Project scope:** Non-commercial student prototype. No Audius account or app-specific provider approval has been obtained. Anonymous API search and playback were tested in one local browser session; this confirms technical operation for sampled tracks, not broader legal clearance or provider approval. This is a technical/product decision, not legal advice.


## Implementation update (October 25, 2026)

Audius search and native HTML audio playback are now implemented in the app. Search uses the official documented `GET /v1/tracks/search` endpoint; playback is started only by a user click and uses the documented `GET /v1/tracks/{track_id}/stream` redirect. The app does not download or persist the redirected media URL. Search results remain internal tracks and are ranked by the existing provider-independent engine.

The mapper enables playback only when the API response explicitly reports the default `All rights reserved` license, streamability, availability and stream access, and reports no deletion, unlisted state, gate, stream conditions, or API-key restriction. This default-license-only interpretation follows the Audius OML's “unless Alternative License” grant, but is not legal clearance; any absent, unrecognized, or alternate license is disabled. Stream requests can still fail after search if a creator removes or restricts a track, and the player displays an error in that case.

Manual browser verification on October 25, 2026 used the live Audius API and browser-native audio. `Day Dreamin' (Electronic Type Beat)[Remake]` by `uezurii.flac` played through the app; the browser audio element reached `readyState: 4`, remained unpaused, advanced its playback time, and reported no media error. Pause, resume, seek, switching to `Electronic Giveaway` by `Brentin Davis`, and Stop were also exercised; the second track loaded and advanced. This verifies playback at that time in this browser only. The earlier attempt exposed and fixed an audio-element replacement bug before successful verification.

No credentials or new dependency were needed for anonymous Audius reads in this local run. The current provider requirements and official references are detailed in [AUDIUS_FEASIBILITY.md](AUDIUS_FEASIBILITY.md). Continue to treat creator rights and specific API access/terms as provider-governed; do not infer universal availability from this successful sample.

## Decision

**Preferred first playback pilot: Audius, conditionally.** Its official API describes search and streaming for third-party music players and discovery apps, read-only endpoints mostly work without credentials, and the Open Music License explicitly grants Music Players rights to stream and transmit licensed material. This is the closest documented fit for the app's independent recommendations and playback goal. Begin only with publicly accessible tracks for which the Audius OML applies and no alternative license or gate overrides access. Preserve creator attribution, Audius/source identity, and a canonical Audius track link. Treat the license and content status as item-level data; an API response or stream URL alone is not proof that an item is playable.

This remains conditional: Audius content is creator-uploaded, users can opt out of API access, select alternate licenses, set access/price restrictions, or gate streams. The OML is a legal license with scope and exceptions that the app must implement correctly. Obtain clarification from Audius if the proposed personalized ranking, recommendation explanations, or UI presentation are not clearly covered. Audius search and playback have now been implemented and manually verified in one browser session; provider approval and broader availability remain unconfirmed.

**Fallback: Jamendo, limited to a non-commercial pilot and individually verified track licenses.** It provides search plus per-track license and audio fields, and documents a stream action. Its API terms are unusually old (last modified 2013), require creator/provider credit and direct content-page backlinks, restrict commercial use without a quote, and say credentials must not be disclosed. Confirm whether a client ID may be used from a browser and whether the planned custom recommendation UI/streaming pattern is permitted before implementing. Jamendo's catalog is primarily independent/Creative Commons-oriented, so it is not a substitute for a broad commercial catalog.

Do not start with SoundCloud or YouTube Data API for the app's own cross-source ranking. SoundCloud currently requires Artist Pro app registration and its terms prohibit certain alternative content aggregation/streaming services unless explicitly licensed. YouTube's API policies restrict derived metrics, combining/aggregating API data, and custom scores absent the applicable approved analytics use case. Spotify Web Playback SDK is technically capable but development access now has a Premium-owner requirement and a five-user cap, playback is for authenticated Premium users, and commercial streaming integrations are not permitted. These are poor first playback paths for this student prototype without provider-specific confirmation or a changed product scope.

MusicBrainz remains metadata-only. It supplies no playable audio, and its search-index/share-alike question already recorded in [MUSICBRAINZ_API_STATUS.md](MUSICBRAINZ_API_STATUS.md) remains unresolved. Never interpret a MusicBrainz recording ID, URL relationship, title match, or artwork availability as playback permission.

## Product paths

| Product path | Feasibility | Recommendation quality | User experience |
|---|---|---|---|
| Search metadata + external official link | Lowest effort; can be a provider-owned search link without claiming a match. If results are sourced through an API, that API's terms still apply. | Recommendation quality comes from licensed internal metadata and user feedback; link target may be approximate. | Simple and robust; playback leaves the app. This is the current MusicBrainz-compatible option, but MusicBrainz itself has no audio. |
| Search metadata + official embedded/provider player | Moderate; source-specific UI and access eligibility required. Audius is the best candidate for a conditional first pilot; SoundCloud and YouTube have additional material restrictions. | Stronger than link-only only if metadata legitimately supports the ranking and sources are clearly distinguished. Keep scoring in the provider-neutral engine. | In-app playback while preserving provider controls/attribution. Some items may be unavailable due to license, creator settings, geography, user eligibility, or provider failure. |
| Open metadata + separately licensed playback catalog | Moderate and architecturally clean. MusicBrainz IDs can support identity matching, but match confidence must be explicit. | Good for title/artist/genre-based first-party ranking if the metadata rights allow it; no invented relationship or audio analysis. | Requires cross-provider matching and can fail to find a play target. ## Architecture for a future implementation

Keep `TrackSearchProvider` and `InternalTrack` as the metadata/search boundary and leave `src/recommendation/**` provider-neutral. Current `InternalTrack` has `source`, `sourceId`, `externalUrl`, and optional `previewUrl`, but no distinct playback capability or provider/license/access status. Do not overload `externalUrl` or synthesize an audio URL.

A small future change should model playback as an optional capability: provider + provider item ID + canonical page URL + allowed mode/status (official embedded player, provider stream, or external link), plus any eligibility/license metadata needed to hide or disable playback. Provider-specific services perform search, validation, and mapping. A UI playback adapter/component handles the approved provider method. Recommendation candidates remain normalized metadata and scores. Like/Skip/Dislike/Favorites/Playlists remain first-party app state. Missing or uncertain playability should show a normal external source link, or no playback action.

### Conditional Audius pilot plan (not yet implemented)

1. Ask Audius developer/legal support to confirm the OML covers this exact non-commercial app: searching public tracks, app-specific feedback ranking and explanations, client-side streaming via official API/SDK, caching only while required for request/UI behavior, and retaining metadata in local favorites/playlists. Ask how to detect and honor alternate licenses, API opt-out, gated/paid and region-restricted tracks; what attribution is mandatory; and whether independent app name/branding is acceptable.
2. After that confirmation, create an Audius account/app/API key only if the documented rate budget warrants it. Basic read-only access is documented without credentials; keep any API secret out of browser code. Start with GET search and per-track stream/URL from the official API/SDK. No user OAuth should be needed for public read-only calls; verify that the exact search and stream routes are anonymous and check rate limits before implementation. A server is not required for public tracks/basic read-only access; it is required for gated track signatures and is out of initial scope.
3. Map only validated ID, title, artist, tags/genre, artwork URL, canonical track URL, access/license state, and a distinct playback capability. Use only public, permitted tracks with no conflicting alternative license. Preserve provider source and source link in the UI, creator attribution, Audius branding/credit as specified, and official player/provider navigation. Do not download, rehost, or cache audio.
4. Handle loading, no results, inaccessible/gated/removed tracks, rate limits, malformed responses and network failures. If an item is not eligible, show its canonical provider page only if allowed; do not expose a dead player button.
5. Add service mapping/error tests and observable app tests. Acceptance: mock behavior remains intact; no secret in client bundle; only eligible items show Play; attribution/source link is present; unavailable item errors are graceful; ranking engine imports no provider module; a manual check uses a real public Audius result and verifies stream plus outbound link.

## Questions requiring provider confirmation

### Audius (before first pilot)
- Does the OML's "Music Player" grant and current API Terms cover a non-commercial web discovery app which computes its own rankings from track metadata and local Like/Skip/Dislike feedback, and shows score explanations?
- How does an API client reliably detect and enforce an alternate license, creator API-access opt-out, paid/restricted visibility, or subsequent track removal? Which fields/endpoints are authoritative, and what attribution is required for commercial vs non-commercial use?
- Are direct API stream responses appropriate in an app-owned UI, or is there an official embedded player that should be used? What caching and artwork display rules apply?

### Jamendo (fallback)
- Is a browser-delivered `client_id` permitted despite the API Terms' credential non-disclosure clause, and is direct browser CORS officially supported?
- Are API stream links usable in a third-party custom ranked player for every displayed Creative Commons license, and what exact attribution/license fields must appear?
- Do non-commercial API terms permit a recommendation UI that combines Jamendo tracks with MusicBrainz metadata or other catalogs?

### SoundCloud / Spotify / YouTube
- SoundCloud: can SoundCloud explicitly license this app's contemplated aggregation, personalized ranking and any player integration; which account tier/API access is currently required, and does the SoundCloud-based product name need changing?
- Spotify: may user-feedback-ranked Spotify tracks be used as personalized recommendations, and which data fields/preview embeds are allowed in this use case under current developer policy?
- YouTube: does user-feedback ranking of videos from `search.list` count as prohibited derived/aggregated API data, or is there a specific approval path for a music-discovery recommender? No public policy exception was found that clearly fits.
